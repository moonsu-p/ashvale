## 1. 컨셉

한 명의 방랑자가 변방에 거점을 세우고, 주(週) 단위로 선택을 쌓아 그 땅의 역사를 만든다.
**게임은 끝나지 않는다.** 엔딩 대신 *시대(Era)* 가 계속 갱신되고, 시대가 오를 때마다 새 지역·인물·건물·위협이 열린다.

### 설계 원칙

1. **네 축이 서로를 먹인다.** 어느 하나만 파면 반드시 막힌다.
   ```
   탐험 → 자원·경험 → 거점 건설 → 시대 상승
                                      ↓
             판정 보정 ← 인물 호감 ← 신규 인물 등장
   ```
2. **판정은 전부 공개한다.** 주사위값과 보정 계산식을 결과 화면에 그대로 노출한다. 숫자가 보여야 "성장했다"는 감각이 생긴다.
3. **캐릭터는 죽지 않지만 거점은 무너질 수 있다.** HP 0은 사망이 아니라 후퇴다. 그러나 기근이나 위협 패배가 누적되면 거점은 실제로 붕괴한다(§15.2). 붕괴해도 **연대기와 업로드 이미지는 보존된다** — 몰락은 끝이 아니라 한 장(章)이다.
4. **연대기가 곧 보상이다.** 플레이 기록이 읽을 만한 텍스트로 축적되는 것 자체가 장기 동기다.
5. **성장은 숫자보다 먼저 화면에 보여야 한다.** 인구가 늘면 걸어다니는 주민이 늘고, 성벽 레벨이 오르면 실제로 거점을 감싸는 타일이 늘어난다. 시각 변화가 없는 성장 요소는 성장으로 체감되지 않는다. 새 스탯을 추가하기 전에 그것이 화면에서 어떻게 보일지를 먼저 정한다.

## 2. 핵심 루프와 시간

- **1턴 = 1주.** 12주 = 1계절, 4계절 = 48주 = 1년.
- 플레이어는 매 턴 **행동 1개**를 고른다. 행동 → 판정 → 결과 → 턴 종료 처리 → 다음 주.
- **건설은 턴을 소비하지 않는다.** 자원이 유일한 제약. (건설까지 턴을 먹으면 성장 체감이 너무 느려짐)

### 턴 종료 처리 순서 (이 순서를 고정할 것)

1. 행동 결과 적용
2. 자원 생산 − 식량 소비 (계절 보정 적용)
3. 신전 회복 등 주간 회복
4. 위협 카운트다운 / 위협 해결
5. 세계 이벤트 판정 (12%)
6. 레벨업 → 시대 판정 → 신규 해금(지역·인물·건물) 판정
7. 주차 증가, 연대기 기록 append
8. 자동 저장

### 계절 보정

| 계절 | 효과 |
|---|---|
| 봄 | 식량 생산 +20% |
| 여름 | 목재·석재 생산 +20% |
| 가을 | 식량 생산 +50% |
| 겨울 | 식량 생산 −50%, 위협 강도 +20% |

## 3. 데이터 모델

```ts
type ResourceId = 'wood' | 'stone' | 'food' | 'gold';
type StatId = 'might' | 'agility' | 'insight' | 'will';
type FactionId = 'guild' | 'oath' | 'grove' | 'tower';

interface GameState {
  schemaVersion: 1;
  createdAt: number;

  hero: {
    name: string;
    level: number;
    xp: number;              // 현재 레벨 내 누적
    hp: number;
    maxHp: number;
    stats: Record<StatId, number>;
    statPoints: number;      // 능력치 배분 대기
    skillPoints: number;
    skills: Record<string, number>;   // skillId -> rank
    relics: string[];
  };

  settlement: {
    name: string;
    buildings: Record<string, number>; // buildingId -> level (0 = 미건설)
  };

  resources: Record<ResourceId, number>;

  world: {
    year: number;            // 1부터
    week: number;            // 1..48
    turn: number;            // 총 경과 턴
    eraIndex: number;
    eraTier: number;         // 최종 시대 이후 무한 등급 (§5)
    unlockedRegions: string[];
  };

  companions: Record<string, CompanionRecord>;   // 관계 대상, §7.8
  patrons: Record<string, PatronRecord>;         // 의뢰인, §7.8
  factions: Record<FactionId, number>;   // -100..100

  threat: null | { id: string; power: number; weeksLeft: number; prepBonus: number };

  chronicle: ChronicleEntry[];   // 최근 200개만 유지
  counters: {
    explores: number;
    threatsWon: number;
    threatsLost: number;
    buildsMade: number;
    collapses: number;        // 붕괴 횟수, §15.2 재기 보정에 사용
    firsts: Record<string, boolean>;   // 마일스톤 중복 기록 방지
  };
}

interface ChronicleEntry {
  year: number;
  week: number;
  season: 0 | 1 | 2 | 3;
  kind: 'quest' | 'build' | 'bond' | 'threat' | 'era' | 'world' | 'milestone';
  text: string;
}
```

**구현 지침:** 모든 수치 테이블은 `src/data/*.ts`에 상수로 분리한다. 판정·생산·해금 로직은 `(state, input, rng) => {state, entries}` 형태의 **순수 함수**로 작성하고 `src/systems/`에 둔다. RNG는 시드 주입 가능한 인터페이스로 감싼다(테스트·재현 목적). React 컴포넌트나 Phaser 씬 안에 규칙 로직을 넣지 않는다.

**시각 상태는 저장하지 않는다.** 건물 배치 좌표, 주민 스프라이트 위치, 맵 크기, 계절 틴트 등은 전부 `GameState`에서 **파생**한다. 이유는 두 가지다 — 세이브 파일이 렌더링 구현에 묶이면 아트를 바꿀 때마다 마이그레이션이 필요해지고, 세이브 용량도 불필요하게 커진다.

- 건물 배치는 `deriveLayout(state)`가 결정론적으로 계산한다. 시드는 `state.createdAt`을 쓴다 → 같은 세이브는 항상 같은 배치를 그린다.
- 주민 스프라이트의 순간 위치처럼 진짜 일시적인 값만 Phaser 씬 내부에 둔다. 새로고침 후 달라져도 무해한 것만 해당한다.

## 4. 캐릭터 성장

### 능력치

시작값 전부 3. 각 능력치는 특정 지역의 탐험 판정에 쓰인다.

| ID | 이름 | 주 용도 |
|---|---|---|
| might | 힘 | 전투 판정, 방어력 |
| agility | 민첩 | 숲·관문 계열 탐험 |
| insight | 통찰 | 유물·고대 유적 판정 |
| will | 의지 | 늪·균열 계열, 공포 저항 |

### 레벨

- 레벨업 필요 XP = `40 + (level - 1) * 25` (레벨 내 누적)
- 레벨업 보상: 최대 HP +3, 스킬 점수 +1, 능력치 점수 +1
- 시작: 레벨 1, HP 20/20, 스킬 점수 1

### 스킬 트리

랭크당 스킬 점수 1개. **상위 스킬은 같은 계열 기본 스킬 2랭크 필요.**

| 계열 | 스킬 | 최대 | 랭크당 효과 | 선행 |
|---|---|---|---|---|
| 전투 | 검술 | 5 | 전투 판정 +1 | — |
| 전투 | 방벽 | 5 | 방어력 +3 | 검술 2 |
| 전투 | 결의 | 3 | 위기 결과 HP 손실 −25% | 검술 2 |
| 탐험 | 추적 | 5 | 탐험 판정 +1 | — |
| 탐험 | 야영 | 3 | 탐험 HP 손실 −1 | 추적 2 |
| 탐험 | 연금 | 3 | 전리품 +15% | 추적 2 |
| 지식 | 고문헌 | 5 | 통찰 판정 +1, 탐험 XP +10% | — |
| 지식 | 감정 | 3 | 유물 발견률 +3%p | 고문헌 2 |
| 지식 | 설계 | 3 | 건설 비용 −8% | 고문헌 2 |
| 통솔 | 웅변 | 5 | 호감 획득 +20% | — |
| 통솔 | 행정 | 5 | 자원 생산 +8% | 웅변 2 |
| 통솔 | 징병 | 3 | 방어력 +4 | 웅변 2 |

> 총 랭크 48개 = 약 48레벨 분량. 그 이후는 **초월 랭크**로 무한히 이어진다 — 최대 랭크를 넘어서도 투자할 수 있고, 초과 랭크마다 비용이 1 SP씩 누진한다(6랭크=2SP, 7랭크=3SP…). 효과는 랭크당 값이 그대로 붙는다.

## 5. 거점과 시대

### 건물

- **다음 레벨 비용 = 기본 비용 × (현재 레벨 + 1)**
- **최대 레벨 없음.** 무한 성장 축.
- 인구 = 전 건물 레벨 합. 이 값이 곧 **거점 지수(power)**.

타일 크기는 **시각 단계**에 따라 커진다. 단계는 레벨 **1 / 4 / 10** 세 개만 둔다 — 매 레벨 스프라이트를 갈면 에셋이 12건물 × N레벨로 폭발한다. 3단계면 총 36개로 CC0 팩에서 조달 가능한 범위다.

| ID | 이름 | 해금 시대 | 기본 비용 | 레벨당 효과 | 점유 타일 (1/4/10단계) |
|---|---|---|---|---|---|
| hall | 회관 | 0 (Lv1 시작) | 목20 석10 | 금화 +1/주 | 2×2 / 2×2 / 3×3 |

**성벽은 예외 처리한다.** 다른 건물처럼 한 자리를 차지하는 게 아니라, 거점 점유 영역의 **둘레를 감싸는 타일 링**으로 그린다. 레벨 1–3은 나무 울타리, 4–9는 석벽, 10+는 탑이 달린 성벽으로 타일셋을 교체한다. 방어력이라는 추상 수치를 화면에서 직접 읽게 만드는 장치이므로 우선순위가 높다.

- 식량 < 0 → **기근**: 부족분 × 3 만큼 금화 손실, 무작위 건물 1개 레벨 −1 (확률 40%, 신전 보유 시 감소), 연대기에 `world` 항목 기록

|---|---|---|---|---|---|---|
| whisper | 속삭이는 숲 | 시대 0 | 9 | 민첩 | 목 4–9, 식 3–7, 금 0–4 | 2 |

> 해금은 시대 도달만으로는 부족하게 한다: **시대 조건 + 이전 지역에서 대성공 1회** 를 모두 만족해야 열린다. "발견"이 사건으로 기록되게 하기 위함.

### 판정 공식

```
roll  = 1d20 + stats[지역.능력치] + 탐험보너스
탐험보너스 = 추적랭크 + floor(서고레벨/2) + 동료보너스(§7.2, 최대값만) + 유물보너스 + 첨탑레벨
margin = roll - 지역.난이도
```

| margin | 결과 | 전리품 | XP | 부수 효과 |
|---|---|---|---|---|
| ≥ +8 | **대성공** | ×1.8 | ×1.5 | 유물 12%, 신규 발견 25% |
| 0 ~ +7 | 성공 | ×1.0 | ×1.0 | 유물 4% |
| −7 ~ −1 | 실패 | ×0.35 | ×0.5 | HP −(위험도/2) |
| ≤ −8 | **위기** | 0 | ×0.25 | HP −위험도, 위협 발생 35% |

- 기본 XP = `지역.난이도 × 1.5`
- HP 손실은 야영 랭크만큼 감소, 결의 랭크로 위기 손실 −25%/랭크
- HP 0 이하 → 사망 아님. **"쓰러진 채 실려 옴"**: HP 1로 회복, 다음 2주 강제 휴식, 금화 20% 손실

### 서사 텍스트

지역마다 결과 등급별 문장 풀을 최소 4개씩 준비한다(총 6지역 × 4등급 × 4 = 96문장). 문장은 `{거점명}`, `{동료명}` 같은 치환 토큰을 지원한다.

## 7. 인물과 평판

### 세력 4개

| ID | 이름 | 성향 |
|---|---|---|
| guild | 상인 길드 | 금화·교역·건설 비용 |
| oath | 은빛 서약 | 방어·위협 보상 |
| grove | 숲의 부족 | 식량·탐험 위험도 |
| tower | 마탑 | 유물·통찰·스킬 |

- 범위 −100 ~ +100. 단계: 적대(≤−40) / 냉담(−39~19) / 우호(20~59) / 동맹(60+)
- 동맹 시 해당 세력 관련 보너스 +1단계 및 전용 사건 발생
- **상충 규칙 (적용 확정):** 마탑 평판이 +5 오를 때 숲의 부족이 −2 내려간다. 반대도 같다. 상인 길드와 은빛 서약 사이에는 상충이 없다

### 7.1 인물은 두 명단으로 나뉜다

이 게임의 인물은 **성별과 역할이 묶인 두 명단**으로 구성된다. 이 구분이 이미지 파이프라인, 대사 작성량, 퀘스트 구조를 전부 결정하므로 가장 먼저 확정한다.

| | **관계 대상** | **의뢰인** |
|---|---|---|
| 성별 | 여성 | 남성 |
| 이름 | **플레이어가 지정** | 프리셋 고정 |
| 이미지 | **플레이어가 업로드**, 슬롯 6개 (§7.6) | 픽셀 스프라이트 1장 + 원형 실루엣. 업로드 없음 |
| 관계 수치 | 호감 0–100 | 신뢰 0–60 |
| 공략 | 가능. 우애·연심 트랙 분기 (§7.5) | 불가. 트랙 없음 |
| 보너스 성향 | 탐험·전투·모험 | 경제·건설·생산 |
| 고유 역할 | 동행 탐험, 대화 사건, 갤러리 | **퀘스트 제공**, 신규 관계 대상 소개 |
| 상한 | 8명 | 6명 (전원 프리셋) |

**두 명단은 서로를 먹인다.** 의뢰인의 퀘스트를 깨야 새 관계 대상이 합류하고(§7.7), 관계 대상과의 동행 탐험 성과가 의뢰인의 신뢰를 올린다. 어느 한쪽만 신경 쓰면 명단이 늘지 않는다.

> **설계 주의:** 의뢰인을 "보너스 붙은 버튼"으로 만들지 말 것. 이들이 퀘스트 발행권을 독점하기 때문에 존재 이유가 생긴다. 의뢰인 없이 관계 대상만 늘리는 경로는 만들지 않는다.

### 7.4 호감을 올리는 방법 — 반복 클릭이 되지 않게

관계 대상에만 적용된다. 교류 연타로 100까지 채울 수 있으면 공략이 아니므로 **네 경로를 모두 써야 상한에 닿게** 한다.

| 경로 | 획득 | 제약 |
|---|---|---|
| 교류 (턴 소비) | +6, 소속 세력 평판 +2 | **동일 인물 연속 교류 시 체감**: 2회차 +4, 3회차 이후 +2. 다른 인물과 교류하면 초기화 |
| 선물 (턴 무소비) | 취향 일치 +12 / 불일치 +4 / 혐오 −3 | 인물당 4주 쿨다운. 취향 힌트는 아는 사이(20)부터 노출 |
| 대화 사건 | 선택지에 따라 +8 ~ −5 | 단계 승급 시 1회 발생. 원형별 사전 작성 |
| 동행 탐험 | 결과에 따라 +5 ~ +15 | 동료(40)부터. 원형과 맞는 지역일 때 보정 |

**호감 상한 게이트:** 교류·선물만으로는 **59가 상한**이다. 60 이상은 대화 사건과 동행 탐험을 통과해야 열린다. 이것이 "공략"이라는 감각의 핵심이다.

- **동행 탐험:** 데려간 인물은 지역 판정에 원형 보정을 주지만, 위기 결과 시 부상해 4주간 교류 불가 + 호감 −8. 위험과 보상이 같이 붙는다
- 동행 성공 시 해당 인물 소속 세력의 의뢰인 신뢰 +2 → 두 명단이 연결되는 지점

### 7.5 관계 트랙 — 우애와 연심

호감 60(벗) 도달 시 **관계 선언 사건**이 발생하고 트랙이 갈린다.

```
                    ┌─ 우애 트랙 ─► 맹우(80) ─► 서약의 벗(100)
낯선 사람 → 벗(60) ─┤
                    └─ 연심 트랙 ─► 연인(80) ─► 백년해로(100)
```

| 항목 | 우애 트랙 | 연심 트랙 |
|---|---|---|
| 진입 조건 | 벗(60) 도달 | 벗(60) + 대화 사건 2회 통과 |
| 수치 보너스 | §7.2 표 그대로 | **§7.2 표 그대로 (동일)** |
| 고유 보상 | **소개 연쇄(신규 인물 유입)**, 전용 퀘스트, 세력 평판 대량 | 이미지 슬롯 추가 해금, 전용 사건, 거점 상주 |
| 되돌리기 | 가능 (호감 하락 시 강등) | 불가. 선언 후 트랙 변경 없음 |

**연심 트랙이 우애보다 수치적으로 강하지 않다.** 연애를 최적 전략으로 만들면 다른 세 축을 파는 플레이가 손해가 된다. 연심의 보상은 전부 콘텐츠다.

- **배타성 없음.** 동시에 연심 트랙에 둘 수 있는 인물 수에 제한이 없고, 질투 페널티도 없다 (§13 결정 11 확정)
- **대신 두 트랙이 서로 다른 것을 준다.** 연심에 제한이 없으면 우애 트랙이 죽은 콘텐츠가 되므로, **소개 연쇄(신규 인물 유입)를 우애 트랙 전용으로 둔다** (§7.7). 우애는 로스터를 늘리고, 연심은 콘텐츠를 늘린다. 전원을 연심으로 밀면 로스터 성장이 멈춘다 — 페널티가 아니라 기회비용이다
- 연심 다수 진행의 실제 비용은 **턴**이다. 진입마다 대화 사건 2회와 동행 탐험을 통과해야 하므로 8명 전원 공략은 상당한 주차를 소모한다
- 연인 도달 시 거점 맵 회관 근처에 해당 인물 스프라이트가 상주한다 (§10.4)

### 7.6 이미지 슬롯 해금

관계 대상 1명이 **여러 이미지를 갖는다.** 슬롯은 관계 진행에 따라 열리고, 열린 슬롯에 플레이어가 이미지를 넣는다.

| 슬롯 | 해금 조건 | 용도 | 권장 규격 |
|---|---|---|---|
| 0 · 기본 초상 | 인물 등장 시 | 대화·목록 기본 이미지 | 512×680 |
| 1 · 표정 변화 | 아는 사이(20) | 대사 감정에 따라 교체 | 512×680 |
| 2 · 전신 | 동료(40) | 동행 탐험 화면 | 480×960 |
| 3 · 사건 삽화 | 벗(60) | 관계 선언 사건 배경 | 900×1200 |
| 4 · 트랙 전용 | 맹우/연인(80) | 트랙별로 다른 슬롯이 열린다 | 900×1200 |
| 5 · 최종 | 100 도달 | 연대기 회상 화면 | 900×1200 |

- **슬롯이 비어 있어도 게임은 정상 작동한다.** §11.1 플레이스홀더 규약을 따르고, 슬롯 0이 있으면 그것으로 대체 렌더한다
- 해금은 **자리가 열리는 것**이지 이미지가 자동 생기는 게 아니다. UI 문구를 정확히 쓸 것: "새 이미지 자리가 열렸습니다 — 추가하기"
- 잠긴 슬롯은 자리와 해금 조건을 함께 보여준다. 무엇을 향해 가는지가 보여야 동기가 생긴다
- **갤러리 화면**: 인물별 해금 이미지를 모아 보는 화면. 연대기와 함께 장기 수집 동기를 담당한다
- 최대 저장량: 관계 대상 8명 × 6슬롯 = **48장** (§11.4 용량 계산의 기준)

### 7.7 관계 대상 유입 경로

시작 3명 외 5자리는 진행 중 채운다. **모든 경로에 의뢰인이 관여한다.**

1. **의뢰인 퀘스트 보상** (주 경로): §7.3 표의 4개 퀘스트가 각각 1명을 데려온다. 퀘스트는 신뢰 20(거래처) 이상에서 발행
2. **표류자 사건** (세계 이벤트, 시대 2+, 주당 3%): "낯선 이가 문 앞에 쓰러져 있다." → 받아들일지 선택. 단, **의뢰인 중 1명 이상이 오랜 벗(40)** 이어야 발생한다 (보증인 필요)
3. **소개 연쇄 (우애 트랙 전용)**: 관계 대상이 **맹우(우애 80)** 에 도달하면 같은 세력의 인물을 소개하는 사건이 발생한다. **연인(연심 80)은 소개하지 않는다** — 두 트랙의 역할 분담이 여기서 성립한다(§7.5)

**인물 생성 흐름 (UI)**

```
사건 발생 → [원형 제시: 2~3개 중 선택] → [이름 입력] → [이미지 추가(건너뛰기 가능)] → 등장
              ↑ 사건이 원형 후보를 제한한다.        ↑ 나중에 인물 화면에서 추가 가능
                6개 전부에서 고르게 하면
                원형의 서사적 의미가 사라진다
```

- 상한 8명 도달 시 새 인물 사건은 "떠나보낼 인물 선택" 또는 거절로 처리한다. 떠난 인물은 연대기에 기록되고 **갤러리와 이미지는 보존**한다
- 이미지를 건너뛴 인물도 정상 플레이 가능하다. 나중에 언제든 슬롯 0부터 채울 수 있다

### 7.8 데이터 모델 (§3 확장)

두 명단은 **타입을 분리한다.** 하나의 레코드에 `isRomanceable` 같은 플래그를 두면 의뢰인에게도 이미지 슬롯 로직이 흘러들어간다.

```ts
interface CompanionRecord {          // 관계 대상 (여성, 커스텀)
  id: string;                        // 생성 시 uuid
  archetypeId: string;               // §7.2의 6종
  name: string;                      // 플레이어 지정
  affinity: number;                  // 0..100
  track: null | 'bond' | 'romance';
  consecutiveTalks: number;
  lastGiftTurn: number;
  clearedEvents: string[];
  injuredUntilTurn: number;
  images: Record<number, string | null>;   // slot -> IndexedDB 키. 값이 아니라 참조만
  unlockedSlots: number[];
  origin: 'preset' | 'quest' | 'drifter' | 'referral';
  joinedTurn: number;
  departedTurn: number | null;       // 떠나도 갤러리 보존용으로 레코드는 남긴다
}

interface PatronRecord {             // 의뢰인 (남성, 프리셋)
  id: string;                        // §7.3의 고정 id
  met: boolean;
  trust: number;                     // 0..60
  questsCleared: string[];
  activeQuestId: string | null;
}

// GameState 확장
companions: Record<string, CompanionRecord>;
patrons: Record<string, PatronRecord>;
```

**이미지는 세이브 JSON에 넣지 않는다.** `images`에는 IndexedDB 키만 저장한다. 처리는 §11.4.

## 8. 위협과 방어

- 발생: 시대 1부터 **6주 주기**, 또는 탐험 위기 결과에서 35%
- 준비 기간 2주. 그 사이 `방비` 행동으로 `prepBonus += 8` 누적 가능
- 위협 강도 = `10 + eraIndex * 12 + floor(turn / 4)` × (겨울 1.2) × (1 + eraTier × 0.1)
- 방어력 = `성벽×3 + 훈련장×2 + 힘 + 방벽랭크×3 + 징병랭크×4 + 동료·의뢰인보너스(각 최대값만) + prepBonus`
- 판정: `방어력 + 1d20` vs `위협강도 + 10`

| 결과 | 효과 |
|---|---|
| 승리 | XP = 강도×2, 금화 = 강도, 관련 세력 평판 +5 |
| 패배 | 전 자원 −30%, 무작위 건물 −1레벨, HP −8, 평판 −3 |

위협 종류는 최소 6개(고블린 무리, 도적단, 역병 매개체, 겨울 늑대, 이단 순례자, 균열의 파편) 준비하고 시대별로 등장 풀을 나눈다.

## 9. 유물·세계 이벤트·연대기

### 유물

시대 게이트가 걸린 목록에서 발견. 각 유물은 **영구 패시브** 1개. 최소 12개 준비.

예: `사냥꾼의 나침반`(탐험 판정 +2) / `이끼 낀 인장`(건설 비용 −10%) / `첫 서약의 반지`(방어 +6) / `별의 조각`(모든 판정 +1, 시대 5+)

### 세계 이벤트 (매 턴 12%)

풍년 / 역병 / 유랑 상인 / 이주민 도착 / 왕실 사절 / 도적 소문 / 별의 비 / 가뭄 — 최소 10개. 자원·평판·HP를 소폭 흔들고 연대기에 기록.

### 연대기

- 최근 200개 항목 유지, 연·주·계절 표시, 종류별 색상 구분
- **마일스톤 항목**은 별도 강조: 시대 전환, 신규 지역 최초 발견, 위협 첫 승리, NPC 맹우 도달, 유물 획득
- 필터(종류별) 제공. 이것이 이 게임의 시그니처 화면이므로 UI 품질을 여기에 집중한다

## 10. 아트 디렉션과 렌더링

### 10.1 스타일 확정

| 층 | 스타일 | 규격 |
|---|---|---|
| 타일맵·스프라이트 | 탑다운 픽셀아트 | 원본 16×16px, **정수배(×2) 스케일로 32px 렌더** |
| 일러스트 | 페인터리(그린 느낌) | **지역 배경 900×1200(세로)**, 인물 초상 512×680, 유물 아이콘 128×128 |
| UI | 픽셀 폰트 금지, 가독성 우선 | 한글 픽셀 폰트는 자모 조합 때문에 품질 확보가 어렵다 |

**아이소메트릭을 쓰지 않는다.** 깊이 정렬과 좌표 변환 비용이 크고, 한국어 UI를 겹칠 때 여백 계산이 까다롭고, CC0 아이소 에셋이 탑다운보다 훨씬 희소하다.

**픽셀 맵 + 그린 일러스트의 조합은 의도된 대비다.** 90년대 콘솔·PC RPG가 쓰던 관행이라 이질감보다 격식으로 읽힌다. 단, 섞이는 지점(초상화가 맵 위에 뜨는 순간)에는 반드시 **픽셀 테두리 프레임**을 둘러 두 층의 경계를 명시한다. 경계 없이 붙이면 조악해진다.

### 10.2 팔레트 잠금 — 가장 중요한 일관성 장치

서로 다른 출처의 에셋이 섞이면 룩이 무너진다. 해결책은 **32색 공용 팔레트를 먼저 확정**하고, 가져온 모든 타일셋을 그 팔레트로 리맵하는 것이다.

- `src/data/palette.ts`에 32개 hex 값을 이름과 함께 고정한다
- 리맵은 빌드 전 1회 스크립트로 처리한다 (`scripts/remap-palette.ts`, 최근접 색 매칭)
- UI 색상도 같은 팔레트에서만 뽑는다. Tailwind 기본 팔레트를 그대로 쓰면 맵과 UI의 색온도가 어긋난다
- 계절 틴트도 팔레트 내 색상으로 정의한다 (봄 연녹 / 여름 채도↑ / 가을 호박 / 겨울 청회)

팔레트 자체는 CC0 공개 팔레트(예: 32색 계열)에서 출발해도 되고 직접 정해도 된다. 중요한 건 **어떤 색을 쓰느냐가 아니라 하나만 쓰는 것.**

### 10.3 렌더링 아키텍처 — 단방향

```
zustand store (GameState = 단일 진실)
        │  구독
        ├──────────────► React UI 오버레이 (자원 바, 패널, 연대기)
        │
        └──────────────► Phaser Game (씬 = 순수 뷰)
                              │
                         입력 이벤트만 위로 (클릭한 건물 id 등)
```

**규칙:**
1. Phaser 씬은 `GameState`를 읽기만 한다. 절대 쓰지 않는다.
2. 씬은 상태 변화를 받아 `syncFromState(state)` 한 곳에서 스프라이트를 갱신한다. 씬 내부에 게임 규칙 분기를 만들지 않는다.
3. 플레이어 입력은 Phaser → 콜백 → 스토어 액션 순서로 흐른다. 씬이 직접 상태를 바꾸면 저장·되돌리기·테스트가 전부 깨진다.
4. React와 Phaser는 DOM 층이 다르다. Phaser 캔버스를 배경에 두고 React UI를 위에 절대배치한다. 캔버스 크기는 `ResizeObserver`로 컨테이너에 맞춘다.

Phaser를 고른 이유는 타일맵 렌더, 스프라이트 풀, 카메라, 트윈, 텍스처 아틀라스가 전부 기본 제공이기 때문이다. PixiJS는 더 가볍지만 그것들을 직접 만들어야 한다.

### 10.4 씬 구성

**SettlementScene (메인 화면)**

거점을 실제 격자 맵으로 보여준다. 이 게임의 얼굴이므로 품질을 여기에 집중한다.

- 격자 크기는 시대에 따라 확장: 시대 0–1은 **12×12**, 2–3은 **18×18**, 4+는 **24×24**

> **v0.6 조정:** 이전 안(16×12 → 24×18 → 32×24)은 데스크톱 가로 화면 기준이었다. 세로 화면 폰은 가로폭 393dp에 32px 타일이 약 12개만 들어오므로, 격자를 정사각에 가깝게 줄이고 세로 스크롤을 활용한다. 성장 체감은 격자 면적이 아니라 **건물 밀도와 성벽 링 확장**으로 낸다.

**모바일 카메라·입력 규칙 (필수)**

- **핀치 줌 0.5×–2.0×, 드래그 팬.** 기본 줌은 1.0×이며 거점 전체가 화면에 안 들어오는 것을 정상으로 본다
- **더블 탭 = 전체 보기.** 현재 점유 영역이 화면에 꽉 차도록 줌을 자동 계산한다. 길을 잃지 않게 하는 탈출구
- **LOD:** 줌 0.75× 미만에서 주민 워커 스프라이트와 파티클을 숨긴다. 건물과 성벽만 남긴다. 저가 기기 성능 확보용
- **터치 타깃:** 32px 타일을 직접 탭하기엔 작다. 건물 히트박스를 스프라이트보다 **가로세로 각 8px씩 크게** 잡고, 히트박스가 겹치면 탭 위치에서 가까운 순으로 목록을 띄운다
- **정수배 스케일 유지:** 줌은 0.5 / 0.75 / 1.0 / 1.5 / 2.0 단계로 스냅한다. 임의 배율은 픽셀아트를 흐리게 만든다
- 화면 상단 55%가 맵, 하단 45%가 UI 시트. UI 시트는 드래그로 접을 수 있고, 접으면 맵이 전체로 확장된다
- 시대 전환 시 **카메라 줌아웃 + 맵 확장** 연출 (1.5초). "커졌다"를 한 번에 전달하는 순간
- 건물 배치는 `deriveLayout(state)` 결정론 계산 — 회관을 중심으로 나선형으로 자리를 채운다
- **주민 워커 스프라이트**: `min(인구, 24)`명이 타일 사이를 랜덤 워크한다. 인구 증가를 화면에서 읽게 하는 핵심 장치
- 계절 틴트 + 파티클 (봄 꽃잎, 겨울 눈). 파티클은 성능 예산 안에서만
- 건물 클릭 → 업그레이드 패널 오버레이
- 위협 준비 기간에는 맵 외곽에 적 스프라이트가 접근해 온다 (2주 = 2단계 접근)

**RegionScene (탐험)**

- 지역 배경 일러스트 전면 + 판정 연출
- 주사위 굴림을 시각화한다: `1d20` 숫자가 돌아가다 멈추고, 보정값이 하나씩 더해지며 최종값이 난이도 선을 넘는지 보여준다. §1 원칙 2(판정 공개)를 그래픽으로 구현하는 지점
- 결과 등급별 화면 효과: 대성공은 섬광, 위기는 화면 흔들림 + 붉은 비네트

**오버레이 (React)**

자원 바(증감 표시), 탭 패널(성장·인물·거점·연대기), 결과 카드, 연대기 화면. 연대기는 Phaser를 쓰지 않고 순수 React로 그린다.

### 10.5 애니메이션 예산

과하면 턴 진행이 답답해진다. **턴 처리 연출 총합 1.2초 이내**, 스킵 가능해야 한다.

- 자원 증감: 숫자 카운트업 400ms
- 건물 업그레이드: 스프라이트 교체 + 먼지 파티클 500ms
- 시대 전환만 예외적으로 1.5초 허용 (드물게 발생하므로)
- `prefers-reduced-motion` 존중: 파티클·흔들림 제거, 연출은 즉시 완료 처리

### 10.7 폰트 — 확정

**CDN에서 불러오지 않는다.** §12.8 비통신 요구사항을 깨뜨린다. 전부 `public/fonts/`에 두고 `@font-face`로 자체 호스팅한다.

| 역할 | 폰트 | 굵기 | 라이선스 | 로딩 |
|---|---|---|---|---|
| 본문·UI·대화 | **Pretendard** | 400, 500 | SIL OFL 1.1 | 초기 번들 |
| 연대기·시대 전환 | **Noto Serif KR** | 400 | SIL OFL 1.1 | **지연 로딩** |

- 두 폰트 모두 OFL이며 수정·재배포·임베딩이 허용된다. 폰트 파일 단독 유료 판매만 금지된다
- **픽셀 폰트를 쓰지 않는다**(§10.1). 한글 자모 조합에서 품질 확보가 어렵다

**서브셋이 필수다.** 한글 폰트를 통째로 넣으면 §10.6의 번들 예산을 폰트 하나가 다 먹는다.

- 서브셋 범위: **한글 완성형 2350자 + ASCII + 한국어 문장부호**. 한자와 미사용 라틴 확장은 제외한다
- 포맷 woff2. 굵기당 300~400KB 수준으로 떨어진다
- 굵기는 **400과 500만** 쓴다. 그 이상은 화면에서 무거워 보이고 용량만 늘어난다
- Noto Serif KR은 **연대기 탭 첫 진입 시 지연 로딩**한다. 초기 화면(거점 맵)에는 필요하지 않다. 이후 서비스 워커가 캐시하므로 한 번만 받는다
- 폴백 스택: `Pretendard, system-ui, -apple-system, 'Apple SD Gothic Neo', sans-serif`

### 10.6 성능 예산

- 목표: 중급 모바일에서 60fps
- 동시 스프라이트 300개 이하 (워커 24명 상한이 이 때문)
- 타일셋·스프라이트는 **텍스처 아틀라스 1장**으로 묶는다
- 일러스트는 지연 로딩 + WebP. 초기 로드에 배경 6장을 다 받지 않는다
- 초기 번들 목표 1.5MB 이하 (일러스트 제외)

## 11. 에셋 파이프라인

### 11.1 플레이스홀더 규약 — 개발이 에셋을 기다리지 않게

**이것을 M0에 먼저 만든다.** 그림이 없어도 게임이 끝까지 돌아야 한다.

```ts
interface AssetEntry {
  id: string;
  kind: 'tile' | 'sprite' | 'illustration' | 'icon';
  path: string | null;              // null이면 플레이스홀더로 렌더
  status: 'placeholder' | 'final';
  license?: { source: string; type: 'CC0' | 'AI-generated'; url?: string };
  placeholder: { color: string; label: string };   // 색과 라벨은 필수
}
```

- 매니페스트는 `src/data/assets.ts` 한 곳에 모은다
- `path`가 없으면 렌더러가 팔레트 색 사각형 + 라벨 텍스트를 그린다
- `?debugAssets=1` 쿼리로 미완성 에셋에 자홍색 외곽선을 표시한다
- 에셋 교체는 매니페스트 한 줄 수정으로 끝나야 한다. 코드에 파일 경로를 직접 박지 않는다

### 11.2 필요 에셋 목록

| 분류 | 수량 | 조달 |
|---|---|---|
| 지형 타일 (초지·흙·길·물·바위·숲) | 약 40 | CC0 팩 |
| 건물 스프라이트 | 12건물 × 3단계 = 36 | CC0 팩 + 조합 |
| 성벽 타일 (3재질 × 코너/직선/탑) | 약 24 | CC0 팩 |
| 주민·적 스프라이트 | 약 10 | CC0 팩 |
| 지역 배경 일러스트 (세로) | 6 | AI 생성 |
| 관계 대상 초상화 | 0 (플레이어 업로드) | §11.4 |
| 관계 원형 실루엣 (플레이스홀더) | 6 | CC0 또는 직접 |
| 관계 대상 상주 스프라이트 | 6 (원형별 1장, 32px) | CC0 팩 |
| 의뢰인 스프라이트 + 초상 | 6 + 6 | CC0 팩 / AI 생성 |
| 유물 아이콘 | 12 | AI 생성 |
| UI 아이콘 (자원 4, 능력치 4, 기타) | 약 16 | CC0 또는 직접 |

AI 생성 25장은 한 번 만들면 끝이라 현실적이다. **스타일 일관성이 유일한 과제**이므로, 프롬프트에 고정 문구(구도·재질감·조명·팔레트)를 공통 접두로 두고 전량을 같은 세션에서 생성한다.

### 11.3 라이선스 규율

- 타일셋은 **CC0만** 사용한다. 출처와 라이선스를 `ASSETS.md`에 전부 기록한다
- AI 생성 이미지는 매니페스트에 `type: 'AI-generated'`로 표기한다
- 기존 게임·애니메이션의 캐릭터나 특정 작가 스타일을 재현하려 하지 않는다. 세계관 어휘(변방 개척지, 은빛 서약, 마탑)로 프롬프트를 쓴다

### 11.4 사용자 업로드 이미지

관계 대상(§7.1) 이미지는 플레이어가 직접 넣는다. 의뢰인은 해당하지 않는다. **여기서 구현이 가장 많이 깨지므로 규칙을 명시한다.**

**저장 위치를 분리한다.**

| 대상 | 저장소 | 이유 |
|---|---|---|
| `GameState` | localStorage (JSON) | 작고 자주 쓴다 |
| 업로드 이미지 | **IndexedDB (Blob)** | localStorage는 약 5MB 한계이고 문자열만 담는다 |

이미지를 base64로 세이브 JSON에 넣으려는 시도를 하지 말 것. 용량이 33% 늘고, 세이브 1회가 수 MB 문자열 직렬화가 되며, 저장 한계를 즉시 초과한다.

- IndexedDB 스토어: `ashvale-images`, 키는 `companion:{id}:slot:{n}`, 값은 Blob. 의뢰인은 업로드가 없으므로 이 스토어를 쓰지 않는다
- `GameState`에는 키 문자열만 남는다 (§7.7)
- 렌더 시 `createObjectURL`로 변환하고, **컴포넌트 언마운트 시 반드시 `revokeObjectURL`** 한다. 안 하면 인물 화면을 오래 열어둘 때 메모리가 계속 샌다
- 참조는 있는데 Blob이 없는 경우(수동 삭제 등)는 플레이스홀더로 폴백하고 조용히 참조를 정리한다. 오류 화면을 띄우지 않는다

**업로드 처리**

**절대 규칙 — 원본을 참조하지 말고 복사한다.** 사용자는 사진첩에서 이미지를 고른 뒤 원본을 삭제할 것이다. 따라서 `content://` URI, `File` 핸들, 파일 경로, File System Access의 파일 핸들 등 **원본을 가리키는 어떤 값도 저장해서는 안 된다.** 선택 즉시 바이트를 읽어 재인코딩하고, 그 결과 Blob만 저장한다. 참조를 저장하면 원본 삭제 시점에 이미지 전체가 조용히 깨진다.

1. 허용 형식: PNG / JPEG / WebP. 그 외는 거절 메시지 표시
2. 원본 파일 크기 상한 8MB, 초과 시 거절
3. 선택 즉시 **바이트를 읽어 리사이즈·재인코딩**한다 (Canvas → WebP, 품질 0.85, 슬롯 권장 규격의 긴 변 기준 축소). 이 시점에 원본과의 연결이 끊긴다
4. **EXIF 회전을 반드시 처리한다.** 폰 사진첩 이미지는 EXIF orientation 값을 갖고 있어 그대로 Canvas에 그리면 눕거나 뒤집힌다. `createImageBitmap(file, { imageOrientation: 'from-image' })`로 읽어 방향을 적용한 뒤 그린다. 재인코딩 과정에서 EXIF는 제거되며, GPS 위치 정보도 함께 사라진다(의도된 동작)
5. 슬롯 권장 비율과 다르면 잘라내지 않고 `object-fit: contain` + 팔레트 배경으로 채운다. 자동 크롭은 얼굴을 자른다
6. 총 이미지 용량이 40MB를 넘으면 경고를 띄운다 (관계 대상 8명 × 6슬롯 = 48장 기준)
7. 슬롯별 **교체·삭제** 가능. 삭제해도 슬롯 해금 상태는 유지된다
8. `createObjectURL`로 만든 URL은 세션 한정이다. **저장하지 않는다.** 렌더할 때마다 저장된 Blob에서 새로 만들고, 언마운트 시 `revokeObjectURL`한다

**사용자에게 알릴 것:** 이미지를 추가한 뒤 사진첩 원본을 삭제해도 게임 내 이미지는 유지된다. 추가 완료 화면에 한 줄로 안내한다 — 원본을 계속 보관해야 한다고 오해하면 폰 저장공간을 불필요하게 점유하게 된다.

### 11.5 저장된 이미지는 갤러리에 노출되지 않아야 한다

게임 안에 복사된 이미지는 **안드로이드 갤러리·사진 앱·파일 관리자에 나타나지 않는다**는 것이 요구사항이다. 아래 규칙을 지키면 보장된다.

**PWA 경로 — 구조적으로 보장됨**

IndexedDB Blob은 파일이 아니라 브라우저 내부 데이터베이스의 레코드다. 안드로이드 갤러리는 MediaStore가 색인한 항목만 표시하고, MediaStore는 DCIM·Pictures·Download 등 공유 저장 영역만 훑는다. 브라우저의 앱 전용 데이터 디렉터리는 색인 대상이 아니므로 노출 경로가 없다. 별도 조치가 필요하지 않다.

**APK 경로 — 쓰는 위치를 고정할 것**

| 위치 | 갤러리 노출 | 사용 |
|---|---|---|
| `Directory.Data` (앱 내부 전용) | 안 됨 | **여기만 쓴다** |
| `Directory.External`, `Documents`, `ExternalStorage` 등 공유 영역 | **노출 가능** | 금지 |
| 앱별 외부 저장 (`/sdcard/Android/data/{pkg}/`) | 대개 안 되지만 파일 관리자에서 보인다 | 사용하지 않음 |

**금지 사항**

1. 이미지를 공유 저장 영역에 쓰지 않는다. `Directory.Data` 외의 위치를 쓰는 코드를 만들지 않는다
2. `MediaScannerConnection.scanFile()`을 호출하거나 `ACTION_MEDIA_SCANNER_SCAN_FILE` 브로드캐스트를 보내지 않는다. 이는 파일을 갤러리에 **등록하는** 동작이다
3. `WRITE_EXTERNAL_STORAGE`, `READ_MEDIA_IMAGES` 권한을 요청하지 않는다. **시스템 포토 피커**(`ACTION_PICK_IMAGES`)를 쓰면 권한 없이 사용자가 고른 항목만 받을 수 있다. 갤러리 전체 접근 권한을 얻을 이유가 없다
4. 만약 어떤 이유로 외부 경로를 쓰게 된다면 해당 디렉터리에 `.nomedia` 파일을 두어 색인을 차단한다. 다만 이는 예비 수단이며, 1번을 지키는 것이 정답이다

**꾸러미 내보내기 시 주의**

- 내보낸 zip은 사용자가 지정한 위치(다운로드 폴더, 공유 대상)에 저장되므로 파일 관리자에서 보인다. zip 안의 이미지는 개별 이미지 파일로 색인되지 않으므로 **갤러리에는 뜨지 않는다**
- 내보내기 과정에서 이미지를 임시로 풀어 쓰지 않는다. 메모리 또는 앱 전용 임시 디렉터리에서만 압축한다. 공유 영역에 임시 파일을 만들면 그 순간 색인될 수 있다

**부수 고려 (선택)**

안드로이드 앱 전환기(최근 앱 목록)는 마지막 화면의 미리보기를 남긴다. 이것까지 가리려면 `FLAG_SECURE`를 설정하면 되지만, 그러면 본인의 스크린샷도 함께 막힌다. §13 결정 24로 남긴다.

**내보내기/불러오기 (§12와 연결)**

- 세이브 JSON 내보내기는 **이미지를 포함하지 않는다.** 이미지 참조만 들어간다
- 별도 `연대기 꾸러미 내보내기`를 제공한다: 세이브 JSON + 이미지 Blob을 zip 하나로 묶는다 (`fflate` 등 경량 라이브러리)
- JSON만 불러온 경우 이미지는 전부 플레이스홀더로 뜬다. **불러오기 화면에 이 사실을 미리 알린다.** 조용히 그림이 사라지면 세이브가 깨진 것으로 오해한다

**규율**

업로드된 이미지는 브라우저 로컬에만 저장되며 어디로도 전송되지 않는다. 서버가 없으므로 공유·업로드 기능 자체를 만들지 않는다. 어떤 이미지를 넣을지는 플레이어 책임이며, 실존 인물의 사진이나 타인의 저작물을 넣는 용도로 안내하지 않는다. 앱 내 안내 문구는 "직접 만들었거나 사용 권리가 있는 이미지를 추가하세요" 한 줄로 둔다.

## 12. 저장·배포·운영

- 키: `ashvale.save.v1`, 값: `GameState` JSON (localStorage)
- 이미지: `ashvale-images` IndexedDB 스토어 (§11.4). **세이브와 수명 주기가 다르다** — 새 게임을 시작해도 이미지 스토어를 바로 지우지 않고, 백업 세이브가 폐기될 때 함께 정리한다
- 자동 저장: 매 턴 종료 시 + 건설/스킬 투자 직후 + 인물 관계 변화 직후
- `schemaVersion` 기반 마이그레이션 함수 체인 (`migrate_1_to_2` 형태)
- 수동 **내보내기/불러오기** 2종: 세이브 JSON 단독 / 이미지 포함 꾸러미(zip)
- `새 연대기 시작`은 2단 확인 + 기존 세이브 자동 백업 키 보관
- 저장 실패(용량 초과·시크릿 모드)는 조용히 넘기지 않는다. 상단에 지속 배너로 알리고 내보내기를 권한다

### 12.1 서버는 필요하지 않다

이 게임은 **완전 무서버**로 동작한다. 이미지 "업로드"는 전송이 아니라 `<input type="file">`로 파일을 읽어 브라우저 저장소에 넣는 동작이며, 데이터는 기기를 떠나지 않는다. 공유·전송 기능을 만들지 않으므로 서버가 개입할 지점이 없다.

### 12.2 지속성 위험 — 안드로이드 기준

| 위험 | 내용 | 심각도 |
|---|---|---|
| ~~Safari 7일 삭제~~ | **비적용.** 7일 무상호작용 시 스크립트 저장소를 삭제하는 정책은 iOS/Safari 전용이며, 안드로이드 Chrome·WebView는 선제 삭제하지 않는다 | — |
| 사용자 조작 | 브라우저 사이트 데이터 삭제, 앱 저장공간 지우기 | 중간 |
| 저장공간 압박 | 최선 노력(best-effort) 모드일 때 기기 여유 공간이 부족하면 축출 대상이 된다. **지속 모드를 얻으면 해소된다** | 중간 → 낮음 |
| 기기 간 분리 | 다른 기기와 세이브가 별개 | 중간 |
| 용량 | localStorage는 5MiB 내외 한계. IndexedDB는 별도 관리되며 훨씬 넉넉해 이미지 48장에는 충분 | 낮음 |

> iOS를 지원하기로 결정이 바뀌면 이 표와 §12.3을 되돌려야 한다. 7일 삭제는 홈 화면 설치 앱만 예외이므로 대응이 달라진다.

### 12.3 대응 — 안드로이드용

1. **`navigator.storage.persist()` 요청.** 이것이 주력이다. 승인되면 사용자가 직접 지울 때만 삭제된다. Chromium은 상호작용 이력으로 자동 판단하며 팝업을 띄우지 않는다. 첫 실행 시 1회 요청하고, 결과를 설정 화면에 표시한다
2. **PWA 설치 유도.** 안드로이드 Chrome에서 홈 화면에 추가하면 WebAPK가 만들어져 런처에 실제 앱처럼 등록되고, 지속 모드 승인 가능성이 올라간다. 서비스 워커로 오프라인 실행도 확보된다. 웹 앱 매니페스트 + 서비스 워커를 M0에 포함
3. **꾸러미 백업 = 공유 시트.** File System Access API(`showDirectoryPicker`)는 **안드로이드 Chrome에서 지원되지 않는다.** 폴더 자동 백업은 불가능하므로, zip을 만들어 Web Share API로 공유 시트에 넘기거나 다운로드 폴더로 내려보내는 방식을 쓴다. 사용자가 구글 드라이브·카카오톡 등 원하는 곳으로 보내게 하면 실질적 백업이 된다
4. **백업 리마인더.** 마지막 내보내기가 20턴 이상 지났으면 상단에 비강제 배너를 띄운다. 자동 백업이 없으므로 이 리마인더의 비중이 더 크다

### 12.4 저장 계층 추상화

나중에 데스크톱 앱이나 동기화로 갈 가능성이 있으므로, 저장 구현을 **인터페이스 뒤에 숨긴다.** 게임 코드는 이 인터페이스만 호출한다.

```ts
interface StorageAdapter {
  loadState(): Promise<GameState | null>;
  saveState(s: GameState): Promise<void>;
  getImage(key: string): Promise<Blob | null>;
  putImage(key: string, blob: Blob): Promise<void>;
  deleteImage(key: string): Promise<void>;
  exportBundle(): Promise<Blob>;          // zip
  importBundle(file: File): Promise<void>;
}
```

- 1차 구현: `WebStorageAdapter` (localStorage + IndexedDB)
- 향후 교체 후보: `TauriAdapter`(실제 파일 저장, 용량·삭제 위험 없음) / `SyncAdapter`(서버)
- 게임 로직에서 `localStorage`나 `indexedDB`를 직접 호출하는 코드를 만들지 않는다. 어댑터 밖에서 저장소 API를 쓰면 이 추상화가 무의미해진다

### 12.5 서버가 정말 필요해지는 시점

**기기 간 동기화를 원할 때뿐이다.** 그때 성격이 달라지는 점을 미리 인지할 것:

- 관계 대상 이미지가 타인의 디스크에 저장된다. 로컬 전용일 때와 프라이버시 성격이 완전히 다르다
- 저장 용량 비용이 발생한다 (사용자당 수십 MB)
- 인증·계정이 필요해지고, 그러면 이 기획서의 "서버 없음" 전제에 걸린 결정들이 연쇄로 바뀐다

동기화가 아니라 **안정성만** 원한다면 서버보다 **Tauri 데스크톱 앱**이 정답이다. 실제 파일에 저장하므로 7일 삭제·용량 한계·브라우저 청소가 전부 사라지고, `StorageAdapter` 교체만으로 전환된다.

### 12.6 배포 형태 — PWA 우선, APK는 선택

**서버는 어느 선택지에서도 필요하지 않다.** 정적 호스팅은 파일을 배달할 뿐 백엔드가 아니며, APK는 에셋을 번들에 담으므로 호스팅조차 없다.

| | **정적 호스팅 + PWA 설치 (1순위)** | Capacitor APK (선택) |
|---|---|---|
| 호스팅 | 필요 (GitHub Pages·Cloudflare Pages 등 무료) | 불필요 |
| 저장 | 브라우저 저장소 + 지속 모드 | 네이티브 파일 |
| 브라우저 데이터 삭제에 안전한가 | 아니오 | **예** |
| 개발 반복 | 폰에서 URL만 열면 됨 | 매번 빌드 |
| 필요 도구 | 없음 | Android SDK, Gradle, JDK, 키스토어 |
| 업데이트 | 자동 (재방문 시) | 수동 재설치 |
| 오프라인 | 서비스 워커로 확보 | 기본 |

**1순위를 PWA로 두는 근거**

안드로이드에서는 지속 모드가 승인되면 저장이 사용자 조작 외에는 삭제되지 않는다. APK의 남은 이점은 "브라우저 데이터 삭제에도 안전"과 "호스팅 의존 없음" 두 가지인데, 그 대가로 안드로이드 빌드 도구 사슬과 키스토어 관리, 수동 업데이트를 감당해야 한다. 개발 초반에는 값이 맞지 않는다.

> **판단이 바뀐 이력:** v0.6에서는 APK를 1순위로 채택했다. 근거는 저장 안정성이었고, 그 위험의 대부분은 iOS/Safari의 7일 삭제였다. 대상이 안드로이드로 확정되면서 근거가 사라졌으므로 순위를 되돌렸다.

**APK로 넘어갈 만한 시점**

- 실제로 브라우저 데이터가 삭제되어 세이브를 잃은 경험이 생겼을 때
- 이미지가 수십 장 쌓여 잃을 것이 커졌을 때
- 호스팅 없이 완전히 독립된 앱으로 만들고 싶을 때 (공개 주소를 두고 싶지 않은 경우 포함)

**PWA → APK 세이브 이전 (필수 요구사항)**

전환은 **새 앱 설치**이므로 브라우저 저장소가 자동으로 따라오지 않는다. 두 저장소는 서로 접근할 수 없다. 이전 경로를 미리 확보해 둔다.

1. PWA에서 **꾸러미 내보내기**(세이브 JSON + 이미지 zip)를 실행한다
2. APK를 설치한 뒤 **꾸러미 불러오기**로 그 zip을 읽어들인다
3. 두 어댑터는 **동일한 꾸러미 형식**을 읽고 쓴다. 형식이 갈라지면 이전이 불가능해지므로 zip 구조를 어댑터 구현과 무관하게 고정한다

- zip 구조: `save.json` + `images/companion_{id}_slot_{n}.webp`
- **이 이전 경로는 M7b(내보내기 구현) 시점에 함께 검증한다.** APK를 만들 때 처음 시도하면 형식 불일치를 늦게 발견한다
- 반대 방향(APK → PWA)도 같은 방식으로 동작해야 한다. 어느 쪽이 원본인지 고정하지 않는다

`StorageAdapter`(§12.4)가 있으므로 그 시점에 `CapacitorAdapter`를 추가하면 게임 로직은 손대지 않는다. 구현 요점:

- 세이브 JSON과 이미지를 앱 전용 디렉터리에 파일로 저장 (`Filesystem` 플러그인, **`Directory.Data` 고정**). IndexedDB를 쓰지 않는다. 다른 디렉터리를 쓰면 갤러리에 노출될 수 있다 — §11.5 참조
- 이미지 경로: `images/companion_{id}_slot_{n}.webp`
- 꾸러미 내보내기는 `Share` 플러그인으로 공유 시트에 전달
- 안드로이드 WebView는 Chromium 기반이므로 Phaser WebGL이 동작한다. 저가 기기를 기준으로 §10.6 성능 예산을 지킬 것

**APK를 선택할 경우의 함정**

1. **키스토어를 잃으면 업데이트가 불가능하다.** 같은 키로 서명하지 않으면 덮어 설치가 되지 않고, 삭제 후 재설치하면 앱 데이터가 초기화된다 — **세이브와 이미지 48장이 전부 사라진다.** 키스토어 파일과 비밀번호 백업은 이 프로젝트에서 세이브 보호와 동일한 우선순위다
2. 스토어에 올리지 않으면 사이드로딩(알 수 없는 출처 허용)이 필요하다. 개인용이면 문제없다
3. 업데이트는 수동 재설치다. 원격 업데이트(OTA)는 서버가 필요하므로 범위 밖(§17)
4. 앱 삭제 시 데이터가 사라지는 것은 정상 동작이다. 앱 내 꾸러미 내보내기를 눈에 띄는 위치에 둘 것

### 12.7a 불러오기 규칙 — 붕괴는 되돌릴 수 없다

꾸러미 내보내기/불러오기는 **데이터 보호**(기기 교체, 저장소 삭제, PWA→APK 이전)를 위한 기능이다. 동시에 붕괴(§15.2)를 되돌리는 수단이 될 수 있으므로 두 목적을 가른다.

**원장 (ledger)**

세이브와 **별도 키**에 작은 기록을 둔다. 불러오기가 이 값을 낮추지 못한다.

```ts
interface Ledger {          // 키: ashvale.ledger.v1
  maxTurnReached: number;
  collapses: number;
  lastCollapseTurn: number;
}
```

**규칙**

1. 불러온 세이브의 `world.turn`이 `ledger.lastCollapseTurn`보다 **앞이면**, 불러오는 즉시 §15.2 붕괴 처리를 재적용한다. 붕괴 이전 상태로는 돌아갈 수 없다
2. 원장은 항상 `max(기존, 불러온 값)`으로만 갱신된다. 낮추는 방향의 갱신을 허용하지 않는다
3. 꾸러미 zip에 원장 스냅샷을 포함한다 (`ledger.json`). 새 기기에는 원장이 없으므로 꾸러미의 값으로 초기화한다 — 이것이 정당한 이전을 살리는 통로다
4. `새 연대기 시작`은 원장을 초기화한다. 의도적인 새 게임이므로 정상이다
5. 불러오기 화면에 결과를 미리 알린다: `이 기록은 제1대의 몰락 이전 시점입니다. 불러오면 몰락이 다시 적용됩니다.`

> **한계를 인지할 것.** 이것은 위조 방지가 아니라 **무심코 되돌리는 것의 방지**다. 로컬 저장소를 직접 편집하면 우회할 수 있고, 그것을 막으려 하지 않는다. 목표는 "무너졌으면 무너진 대로 간다"가 기본 동작이 되는 것이다.

### 12.7 업데이트와 데이터 보존

게임은 계속 수정될 것이므로, **업데이트가 세이브를 지우지 않는다는 보장**이 명세에 있어야 한다.

**PWA 경로**

| 상황 | 데이터 |
|---|---|
| 코드를 고쳐 **같은 주소**에 재배포 | **유지.** 저장은 출처(origin)에 묶여 있고 출처가 그대로다 |
| 서비스 워커 갱신, 캐시 버전 변경 | **유지.** 캐시와 저장소는 별개다. 서비스 워커 활성화 시 저장소를 지우는 코드를 넣지 말 것 |
| **배포 주소 변경** (도메인·경로 변경 포함) | **소실.** 새 출처는 저장소를 공유하지 않는다 |
| 브라우저 사이트 데이터 삭제 | 소실 |

- **주소를 바꾸기 전에 반드시 꾸러미를 내보낸다.** 이 사실을 README와 설정 화면에 적어 둘 것
- `github.io/repo-a` → `github.io/repo-b` 같은 경로 변경도 출처 기준이 달라질 수 있으므로 동일하게 취급한다
- 서비스 워커 업데이트 로직에서 `caches.delete()`는 써도 되지만 IndexedDB나 localStorage를 건드리는 코드는 절대 넣지 않는다

**APK 경로**

| 상황 | 데이터 |
|---|---|
| **같은 패키지명 + 같은 키스토어**로 서명한 APK 덮어 설치 | **유지.** 앱 전용 디렉터리가 보존된다 |
| 다른 키로 서명 | 덮어 설치 거부 → 삭제 후 재설치 → **소실** |
| 앱 삭제 후 재설치 | 소실 |
| 설정에서 저장공간 지우기 | 소실 |
| `versionCode` 증가, 코드·에셋 변경 | 유지. 데이터와 무관하다 |

- 따라서 APK 경로의 데이터 안전은 **키스토어 보관에 전적으로 달려 있다.** 키스토어 파일과 비밀번호를 세이브 백업과 같은 수준으로 관리할 것
- `AndroidManifest.xml`에서 데이터 삭제를 유발하는 설정을 건드리지 않는다

**스키마 변경 시**

코드 수정으로 `GameState` 구조가 바뀌는 경우가 업데이트의 대부분이다. 이때 데이터는 남아 있어도 **읽지 못하면 소실과 같다.**

- `schemaVersion`을 올리고 `migrate_N_to_N+1` 함수를 반드시 작성한다 (§12)
- 마이그레이션 실패 시 **덮어쓰지 말고** 원본 세이브를 백업 키로 보존한 뒤 오류를 표시한다. 실패한 세이브를 조용히 초기화하는 것이 가장 나쁜 동작이다
- 필드 삭제보다 무시를 택한다. 쓰지 않는 필드를 남겨두는 비용은 거의 없다

### 12.8 외부 통신 없음 — 검증 가능한 요구사항

이 게임은 **런타임에 어떤 네트워크 호출도 하지 않는다.** 선언이 아니라 검증 가능한 요구사항으로 취급한다.

**금지 사항**

1. **CDN 참조 금지.** 폰트·라이브러리·아이콘을 런타임에 원격에서 불러오지 않는다. 한글 웹폰트는 반드시 **자체 호스팅(번들)** 한다. Google Fonts 링크 태그 한 줄이 이 요구사항을 깨뜨린다
2. **분석·크래시 리포팅 금지.** Sentry, Google Analytics, 텔레메트리, 원격 로깅을 붙이지 않는다. "관행"으로 추가하지 않을 것
3. **원격 소스맵·자동 업데이트 확인 금지**
4. **§13 결정 2(LLM 서사 생성)를 켜면 이 요구사항이 깨진다.** 두 요구사항은 양립하지 않는다. 서사 생성을 도입하려면 이 절을 명시적으로 폐기하는 결정이 선행돼야 한다

**경로별 실제 통신량**

| | 통신 |
|---|---|
| PWA, 첫 로딩 | 호스팅에서 앱 파일을 받는다. 데이터가 나가는 것이 아니라 코드가 들어온다 |
| PWA, 이후 실행 | 서비스 워커 캐시로 오프라인 동작. 재방문 시 갱신 확인 요청이 있을 수 있다 |
| APK | **0.** 설치 후 통신이 전혀 없다 |

**APK에서의 구조적 차단**

`AndroidManifest.xml`에서 `android.permission.INTERNET`을 **제거한다.** 에셋이 전부 로컬 스킴에서 제공되므로 이 권한 없이 동작할 수 있다. 제거하면 통신이 OS 수준에서 불가능해져 약속이 아닌 보장이 된다.

- 제거 후 전체 기능을 확인한다. 특정 플러그인이 이 권한을 요구하면 그 플러그인을 걷어내는 쪽을 택한다
- 권한 목록에 `INTERNET`이 없다는 것 자체가 사용자에게 보이는 증명이 된다

**검증 절차 (M10 완료 조건에 포함)**

1. 기기를 **비행기 모드**로 두고 전체 기능을 한 바퀴 플레이한다 — 탐험, 건설, 이미지 추가, 갤러리, 내보내기까지
2. 웹 빌드에서 DevTools 네트워크 탭을 열고 초기 로딩 이후 요청이 **하나도** 없는지 확인한다
3. 번들 결과물에서 `http://`·`https://` 문자열을 검색해 런타임 참조가 남아 있지 않은지 확인한다
4. APK라면 권한 목록에 `INTERNET`이 없는지 확인한다

### 12.9 APK를 만들려면 실제로 필요한 것

이 문서를 구현 에이전트에 넘기면 **기본값은 웹(PWA) 빌드다.** APK를 원하면 M11을 명시적으로 지시해야 하며, 아래가 갖춰져야 한다.

**로컬 빌드**

| 필요 | 비고 |
|---|---|
| Node.js | 웹 빌드용, 이미 필요 |
| JDK 17+ | 최근 Android Gradle Plugin 요구 사항 |
| Android SDK (Android Studio 또는 cmdline-tools) | 첫 설치 시 수 GB |
| 키스토어 | `keytool`로 생성. JDK에 포함. **분실 시 업데이트 불가(§12.7)** |

구현 에이전트는 Capacitor 구성, `android/` 생성, Gradle 빌드 명령 실행까지 할 수 있으나 **위 도구가 없으면 빌드 단계에서 실패한다.** 코드 작성과 빌드 환경은 별개다.

**대안 — GitHub Actions 빌드 (권장)**

로컬에 안드로이드 SDK를 설치하지 않고 APK를 얻는 방법.

- 워크플로에서 JDK와 Android SDK를 설치하고 `assembleRelease`를 실행한 뒤 APK를 아티팩트로 올린다
- 키스토어는 base64로 인코딩해 저장소 비밀값에 넣고 빌드 시 복원한다. **저장소에 키스토어 파일을 커밋하지 않는다**
- 무료 사용량으로 충분하다
- 구현 에이전트에게 워크플로 파일 작성을 함께 지시할 것

## 15. 문체 · 난이도 · 세션

세 항목 모두 플레이어가 확정했다. 구현 시 임의로 바꾸지 말 것.

### 15.1 문체 — 층마다 다르게

**연대기·판정 결과·시대 전환은 문어체**, **인물 대화와 UI는 현대 구어체.** 두 층을 의도적으로 갈라 대비를 만든다.

| 층 | 문체 | 예 |
|---|---|---|
| 연대기 항목 | 무주어, 과거형 종결(`~했다`), 한자어 허용, 감정어 절제 | 서벽을 세 자 높였다. 인구가 열넷으로 늘었다. |
| 시대 전환 | 문어체, 한 문장으로 짧게 | 성벽 위에 깃발이 걸렸다. |
| 탐험 결과 서술 | 문어체, 다만 사건 위주 | 관문 아래에서 부러진 창대를 거두었다. |
| 인물 대화 | 현대 구어체 | 오늘은 좀 걸을 만하네요. 같이 나가실래요? |
| UI 라벨·버튼 | 간결한 명사형 또는 동사원형 | `건설`, `동행 요청`, `꾸러미 내보내기` |
| 오류·안내 | 평서체, 무엇을 하면 되는지 명시 | 석재가 12 부족합니다. 채석장을 올리거나 교역하세요. |

**호감 단계에 따라 인물의 말투가 바뀐다.** 수치가 아니라 문체로 관계 진행을 체감시키는 장치이므로 대사 작성 시 반드시 반영한다.

| 단계 | 말투 |
|---|---|
| 낯선 사람 · 아는 사이 | 존댓말, 거리감 있는 호칭 |
| 동료 | 존댓말이지만 편해짐, 농담 허용 |
| 벗 · 맹우 | 반말, 이름 부름 |
| 연인 | 반말, 호칭 변화 (원형별로 다르게) |

- 주인공을 부르는 말은 인물마다 고정한다. 원형 데이터에 `호칭` 필드를 둔다
- 연대기에서 주인공은 무주어로 처리한다. `그대`·`당신` 같은 2인칭을 쓰지 않는다 — 기록체와 어긋난다

### 15.2 난이도 — 냉정하게, 그러나 기습하지 않게

플레이어 선택: **붕괴가 실제로 가능하다.** 다만 §1 원칙 3(캐릭터 영구 사망 없음)과 "끝나지 않는 게임" 전제는 유지된다. 둘을 이렇게 가른다.

- **캐릭터는 죽지 않는다.** HP 0은 여전히 "쓰러진 채 실려 옴"이다
- **거점은 무너질 수 있다.** 이것이 이 게임의 진짜 실패 상태다
- **연대기는 무너지지 않는다.** 거점의 몰락은 끝이 아니라 한 장(章)이다

**붕괴 조건**

다음 중 하나를 만족하면 붕괴 판정에 들어간다.

1. 식량이 0 미만인 상태가 **4주 연속** 지속되고 인구가 3 이하
2. 위협 패배로 회관(hall) 레벨이 0에 도달

**붕괴 시 처리**

| 대상 | 처리 |
|---|---|
| 건물 | 전부 초기화. 회관 Lv1만 남는다 |
| 자원 | 0. 재건 지원으로 목재 20 · 식량 20 지급 |
| 시대 | **1단계만 하락.** 0으로 떨어지지 않는다 |
| 캐릭터 레벨·능력치 | 유지 |
| 스킬 | 랭크 절반 회수 후 스킬 점수로 환급(재배분 가능) |
| 유물 | 절반 유실(무작위) |
| 관계 대상 | 호감 절반 하락. 벗(60) 미만은 떠난다(레코드는 `departedTurn`으로 보존) |
| **업로드 이미지** | **100% 보존. 예외 없음** |
| 연대기 | 보존. `milestone` 항목으로 몰락이 기록되고 새 장이 시작된다 |
| 갤러리 | 보존 |

- 붕괴 횟수를 `counters.collapses`에 기록한다. 붕괴 1회당 시대 상승 임계값(§5)을 **5% 완화**한다. 반복 좌절을 막는 재기 보정
- 붕괴는 세대 교체로 표현한다. 연대기 표기: `제2대 아쉬베일`

**냉정함은 "예고 없음"이 아니라 "되돌리기 어려움"으로 구현한다.** 기습은 재미가 아니라 불신을 만든다.

- 식량이 마이너스로 전환된 주부터 상단에 경고 배너를 상시 표시한다
- 붕괴 판정 2주 전부터 문어체 경고를 연대기와 화면에 함께 띄운다: `이 거점은 겨울을 넘기지 못할 것이다.`
- 위협 준비 기간에 현재 방어력과 위협 강도를 **숫자로 나란히** 보여준다. 이길 수 없는 싸움임을 알 수 있어야 한다
- 붕괴 직전 1주에 한 번, 자원을 대가로 시간을 버는 선택지를 제공한다(예: 유물 1개를 팔아 식량 확보). 구제가 아니라 **거래**다

### 15.3 세션 — 짧게도 길게도

플레이어 선택: 5–10턴 세션과 20–40턴 세션이 모두 성립해야 한다. 요구사항이 갈린다.

**짧은 세션 대응**

- **재개가 즉각적이어야 한다.** 앱을 열고 3초 안에 다음 행동을 고를 수 있어야 한다. 스플래시·로고·인트로 애니메이션을 넣지 않는다
- 한 턴이 **5초 안에 완결**되어야 한다(연출 1.2초 + 읽는 시간)
- 매 턴 자동 저장(§12). 5턴만 하고 닫아도 손실이 없어야 한다
- 앱을 열면 **직전 연대기 항목 1~2줄**을 상단에 보여준다. 어디까지 했는지 다시 파악하는 비용을 없앤다
- 위협 준비 기간 2주 같은 타이머는 실시간이 아니라 턴 기준이므로 세션이 끊겨도 안전하다. 실시간 타이머를 도입하지 않는다

**긴 세션 대응**

- 같은 행동을 반복할 때 **재실행 버튼**을 제공한다(직전 행동 한 번 더). 메뉴를 다시 파고들지 않게
- 연출 스킵: 화면 아무 곳을 탭하면 진행 중 연출이 즉시 완료된다
- 40턴 연속 플레이에서 자원 숫자가 커져도 UI가 깨지지 않게 자리수를 확보한다(6자리)
- **일괄 자동 진행은 만들지 않는다.** 선택이 이 게임의 내용이므로, 자동화하면 남는 것이 없다

**밸런스 기준선**

기획서 §14의 밸런스 목표표(10주 / 30주 / 60주 / 120주)를 유지한다. 짧은 세션 기준으로 **한 세션(약 7턴)마다 눈에 보이는 변화 1개**가 목표다 — 건물 레벨업, 새 인물, 스킬 랭크, 지역 해금 중 최소 하나.

## 16. 퀘스트 · 온보딩 · 대화 사건 · 교역 · 선물

v1.4에서 채운 누락 시스템. 앞선 결정(문체 §15.1, 냉정한 난이도 §15.2, 양쪽 세션 §15.3, 연심 다수 허용 §7.5)을 전제로 설계했다.

### 16.1 퀘스트

관계 대상 유입이 전부 퀘스트에 걸려 있으므로(§7.7) 뼈대를 먼저 정의한다.

**원칙**

- **동시 수락 1개.** 짧은 세션에서 목표가 흐려지지 않게 한다. 여러 개를 병렬로 관리하는 재미는 이 게임이 노리는 것이 아니다
- **기한 없음, 실패 없음.** 세션 길이가 자유롭기 때문에(§15.3) 실시간·턴 제한을 걸면 짧게 플레이하는 사람이 손해를 본다
- **별도 미니게임 없음.** 퀘스트는 기존 행동(탐험·건설·교류)으로 자연히 진행된다. 새 상호작용을 만들지 않는다
- **완료는 자동이 아니다.** 조건을 채운 뒤 해당 의뢰인과 교류할 때 보고·완료된다. 만나러 가는 동작이 관계를 만든다

**구조**

```ts
interface Quest {
  id: string;
  patronId: string;
  title: string;
  requirements: QuestReq[];      // 전부 충족해야 완료 가능
  reward: QuestReward;
}
type QuestReq =
  | { kind: 'exploreSuccess'; regionId: string; count: number }
  | { kind: 'buildingLevel'; buildingId: string; level: number }
  | { kind: 'payResource'; resource: ResourceId; amount: number }
  | { kind: 'threatsWon'; count: number }
  | { kind: 'factionRep'; factionId: FactionId; value: number };

// GameState 확장
activeQuest: { questId: string; progress: Record<string, number>; acceptedTurn: number } | null;
```

**퀘스트 정의**

| 의뢰인 | 제목 | 요구 | 보상 |
|---|---|---|---|
| 바르텍 | 교역로 개척 | 무너진 관문 성공 3회 + 금화 60 | 관계 대상 1명 (merchant 제외 원형 중 2개 제시) |
| 토바 | 채석장 증축 | 채석장 Lv3 + 석재 80 | 성벽 재질 해금 (석벽 조기 개방) |
| 하를 | 서약의 시험 | 위협 승리 2회 + 훈련장 Lv2 | 관계 대상 1명 (knight / envoy 중 선택) |
| 오렌 | 고문헌 해독 | 서고 Lv2 + 통찰 판정 대성공 1회 | 다음 지역 즉시 해금 |
| 도란 | 이주민 유치 | 농장 Lv4 + 식량 120 | 관계 대상 1명 (herbalist / hunter 중 선택) |
| 벨 | 은밀한 서신 | 세력 평판 2곳 40 이상 | 관계 대상 1명 (wanderer 고정) |

- 제시 조건: 해당 의뢰인 신뢰 20(거래처) 이상 + 이미 수락한 퀘스트가 없음
- 거절 가능. 거절해도 신뢰가 깎이지 않고 다음 교류에서 다시 제시된다
- 진행 상황을 행동 화면 상단에 한 줄로 상시 표시한다 (`무너진 관문 성공 2/3`)
- **붕괴 시(§15.2) 진행 중 퀘스트는 초기화된다.** 수락 자체도 취소되며 다시 제시받아야 한다

### 16.2 첫 5분 — 온보딩

**스플래시·로고·인트로 애니메이션을 넣지 않는다** (§15.3 재개 3초 규칙과 충돌).

```
[화면 1]  제목 + 버튼 하나: 「연대기를 시작한다」
             ↓
[화면 2]  이름 입력 (기본값 제시) · 거점 이름 입력 (기본값 아쉬베일)
             ↓
[화면 3]  문어체 3문장 도입 → 탭하면 즉시 거점 화면
             ↓
[1주차]   과제 카드 1개 + 권장 행동 강조
```

**도입 문장 (문어체, §15.1)**

> 변방의 이름 없는 땅에 천막을 세웠다.
> 왕도의 지도에는 아직 이곳이 없다.
> 첫 주가 시작된다.

**강제 튜토리얼은 만들지 않는다.** 대신 두 장치로 대체한다.

1. **과제 카드**: 화면 상단에 현재 목표 1개를 문어체 한 줄로. 순서는 고정 — 농장 세우기 → 탐험 1회 → 목재소 세우기 → 세리아와 교류 → 시대 1 도달. 다섯 개를 마치면 카드가 사라지고 다시 나타나지 않는다
2. **권장 행동 강조**: 첫 5턴 동안 과제와 관련된 행동 버튼에 은은한 테두리. 강제하지 않고, 다른 행동을 골라도 막지 않는다

- 세리아(knight)는 **3주차에 자동 등장**한다. 첫 인물을 플레이어가 찾아내게 하지 않는다
- 이미지 추가 안내는 세리아 등장 시 1회만. 건너뛰기 기본값
- 첫 탐험은 속삭이는 숲(난이도 9)이고 시작 민첩 3이면 성공률이 충분하다. 첫 판정이 실패로 시작하지 않게 이 수치를 낮추지 말 것

### 16.3 대화 사건

호감 60 게이트(§7.4)의 핵심이므로 구조를 확정한다.

**원칙: 주사위를 굴리지 않는다.** 탐험은 판정이지만 대화는 선택이다. 대화에 확률을 넣으면 취향을 파악하는 재미가 사라진다.

```ts
interface DialogueEvent {
  id: string;
  archetypeId: string;
  tier: 20 | 40 | 60 | 80;       // 어느 단계 승급에서 발생하는가
  situation: string;              // 3~5문장, 구어체 (§15.1)
  choices: { text: string; affinity: number; factionShift?: [FactionId, number] }[];
}
```

- 원형별 **4개** (tier 20/40/60/80) × 6원형 = **24개**
- 선택지는 3개. **정답이 없다.** 호감 +8 / +4 / −2 정도로 갈리며, 마이너스 선택지도 세력 평판을 올리는 등 다른 것을 준다
- 판단 근거는 **취향 힌트**(아는 사이 20부터 노출)와 그 인물의 이전 대사다. 정보를 모아둔 사람이 유리해야 한다
- 같은 사건은 반복되지 않는다 (`clearedEvents`)
- tier 60 사건 2회 통과가 연심 트랙 진입 조건이다 (§7.5)
- 말투는 그 시점의 호감 단계를 따른다 (§15.1 말투 표)

### 16.4 교역

§5에서 시장이 "교역 해금"이라고만 되어 있어 정의가 비어 있었다.

- 시장 Lv1에서 해금. **턴을 소비하지 않는다**
- 판매 기본 환율

| 자원 | 판매 | 구매 |
|---|---|---|
| 목재 | 3 → 금화 1 | 금화 2 → 목재 3 |
| 석재 | 2 → 금화 1 | 금화 3 → 석재 2 |
| 식량 | 3 → 금화 1 | 금화 2 → 식량 3 |

- **환율 개선**: 시장 레벨당 판매가 +5%, 바르텍 거래처(20) +10%, 오랜 벗(40) +20% (합산)
- **주간 거래 한도 = 시장 레벨 × 30 금화 상당.** 한도가 없으면 자원을 무한 환전해 건설 곡선이 무너진다
- 겨울에는 식량 구매가가 50% 상승한다. 계절 대비를 유도하는 장치
- 붕괴 직전 구제 거래(§15.2)는 이 한도를 무시한다

### 16.5 선물 품목

§7.4에서 취향이 "무구·석재" 같은 카테고리인데 선물은 금화 소비로만 되어 있어 일치 판정이 불가능했다.

| 품목 | 금화 | 카테고리 |
|---|---|---|
| 잘 벼린 검 | 30 | 무구 |
| 필사한 서적 | 25 | 서적 |
| 다듬은 가죽 | 15 | 가죽 |
| 장인의 도구 | 20 | 도구 |
| 은세공 예물 | 40 | 예물 |
| 희귀한 씨앗 | 15 | 씨앗 |
| 자원 직접 전달 | — | 목재 / 석재 / 식량 (자원 20 소비) |
| 유물 양도 | — | 유물 1개 소멸 |

- 시장이 없어도 자원 직접 전달과 유물 양도는 가능하다. 시장 Lv1부터 나머지 품목 구매 가능
- 판정: 원형 취향과 **일치 +12 / 불일치 +4 / 혐오 −3** (§7.4). 유물 양도는 취향 무관 **+25**
- 취향 힌트는 아는 사이(20)부터 노출. 그 전에는 불일치를 감수하고 찔러보거나 자원을 준다
- 인물당 4주 쿨다운 (§7.4)
